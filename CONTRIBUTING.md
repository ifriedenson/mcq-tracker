# Contributing to MCQ Tracker

Thanks for helping. This repository is a dependency-free Obsidian plugin: the
source lives in `src/`, and `main.js` is generated by `scripts/build.js`.

## AI-assisted contributions

AI assistance is allowed, but you are responsible for the result. Disclose
substantial AI-generated code in the pull request, review every line yourself,
and make sure you have the right to license what you submit.

## Before you open a pull request

```bash
npm ci --ignore-scripts --no-audit --no-fund
npm test                  # full suite
npm run check             # main.js matches src/ and no dynamic execution exists
```

If you change `src/`, run `npm run build` and commit the regenerated `main.js`
with the source change. Do not edit `main.js` by hand.

## Releasing

The version in `manifest.json` is the release: a push to `main` with a new
version publishes it through `.github/workflows/release.yml`.

1. Bump the version in `package.json`, `manifest.json` and `versions.json`.
2. Write `docs/release-notes/<version>.md`.
3. Run `npm run build` and commit `main.js` with the source change.
4. Run `npm run plan:status`. It runs the suite and rewrites the status block in
   `plan.md` (version, test and failure counts, source-file and module counts,
   bundle size, checked/partial/unchecked rows). Commit `plan.md` in the same
   commit as the version bump; CI and the release workflow reject a release
   whose status block does not match `manifest.json`, `src/`, `vendor/` and
   `main.js`.
5. Run `npm run check` and `git diff --check`.

`npm run plan:status:check` checks the block without running the suite (it
cannot re-derive the test count, so the recorded count is kept).

## Rules for a change

- Keep the plugin dependency-free. Do not add runtime or development packages.
- Make the smallest change that solves the problem, in the existing module style.
- Add or update tests for behavior changes. The suite uses Node's built-in runner.
- Update `plan.md` when the change affects the roadmap or a documented decision.
- Never add `eval`, `new Function`, string-based timers or dynamic note code.
- Keep user data and review history untouched unless the change is explicitly
  about it, and never overwrite an existing note silently.
- Do not commit secrets, API keys, vault paths or personal data.

## Reporting bugs and security issues

Open a GitHub issue with the plugin version, Obsidian version, platform and the
steps that reproduce the problem. Do not include API keys, private vault
content or other secrets in an issue, a log or a screenshot.
