# 1.301.4 — Recover locked installs and protected imports

An import could stop on a password-protected PDF, and a saved OpenCode install
folder could fail to start with a Windows permission error even though the
executable was inside it. This release makes both recoverable, gives unreadable
files a useful next step, and cleans up an attempt that creates no notes.

## What changed

### Password-protected and damaged files

- The import window now asks for an encrypted PDF's password, retries a wrong
  password, and can skip that one file without stopping the batch.
- The password is used only while the import window is open. It is not saved to
  settings, notes or the vault.
- A batch asks once per encrypted PDF and reuses that password for the rest of
  its pages and pictures.
- Empty PDFs, zero-byte files and damaged Office files now explain that the
  file is empty or damaged and suggest saving a new copy or exporting a PDF.
- Files over **80 MB** are refused from their file metadata and again from their
  actual bytes before a copy is made. All four document import surfaces use the
  same limit.
- A Direct AI page-reading request now has a **3-minute per-chunk limit**, so one
  stalled request cannot leave the import waiting forever.
- Import folders use vault-safe names for characters Windows does not allow,
  and same-name or case-only files get distinct folders. An existing note is
  never overwritten.

### Cleaner stops and failed attempts

- Closing the import window now cancels an in-flight AI or OpenCode wait and
  releases a pending PDF-password prompt instead of leaving the import pending.
- If an attempt finishes with no notes, the copied source, captured pictures and
  empty folders it created are removed. The summary says what was cleaned up.
- A mid-batch cancel after one file is committed keeps that completed file and
  removes only the attempt that was in progress.

### OpenCode install repair

- A saved OpenCode path that points at its install folder now resolves to the
  `opencode.exe` inside it. The folder itself is never passed to the process
  launcher, which caused the Windows `EPERM` error.
- A managed folder whose executable is missing is repaired. The app first uses
  another valid installed copy, otherwise it runs the normal confirmed
  installer and then starts the server.
- A locked old version folder no longer fails a new install. The new copy is
  unpacked beside it and the old folder is cleaned up later, best effort.
- If the process launcher still refuses a path, the error names the path and
  points back to the **OpenCode program** setting instead of showing a raw
  `spawn EPERM`.

## Verification

- `node --test`: **2,684 tests, 2,684 pass, 0 fail, 0 skipped**.
- New coverage drives encrypted PDFs through the real import modal, refuses
  empty and oversized files before writes, and exercises the OpenCode lifecycle
  from realistic on-disk install folders, including a locked old version and a
  managed folder whose executable is missing.
- The request timeout is held referenced, so it still fires when it is the only
  pending work (the case that failed the first Node 20 release run); the full
  suite passes on Node 20 and the current Node.
- `npm run check` is clean across **360 source files**; `main.js` is
  **7,200,452 bytes** on disk from **363 modules**.

No note format, review schedule, setting key, dependency, provider or default
network path changed. PDF passwords remain in memory for the open import only.
