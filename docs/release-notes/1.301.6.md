# 1.301.6 — The agent can always write the notes

## What changed
- **File edits are always allowed for the managed OpenCode server.** When the
  plugin starts OpenCode it now passes an inline config
  (`OPENCODE_CONFIG_CONTENT`, loaded last and therefore winning over the
  user's own config) with `permission.edit: "allow"`. A stored
  `permission: { edit: "ask" }` used to leave every note write waiting for an
  approval the import window cannot show, so the agent appeared to stall until
  the watchdog stopped the file.
- **The vault is explicitly reachable.** When the server's working directory
  is not the vault, the vault counts as an external directory; the same inline
  config allows edits under `<vault>/**` (backslashes normalized to `/`).
- **Only edits are touched.** Reads, bash and every other permission keep the
  user's values, and an `OPENCODE_CONFIG_CONTENT` the user set themselves is
  never overwritten.

## Why
A two-PDF OpenCode-agent import produced no notes: the agent started, then sat
on a file-edit permission prompt with no way to answer it, and the watchdog
ended the file. 1.301.5 made that failure legible; this release removes the
cause for the server the plugin controls.

## Limits
- A server the user runs themselves (AI backend pointed at an external URL)
  keeps its own config; the plugin can only set the environment of the process
  it spawns.
- This does not allow `bash` or any other tool, and it does not change the
  plugin's own review-before-write path in Direct AI.

## Verification
- New `tests/opencode-permissions.test.js` (4 tests): the helper allows edits
  and leaves read/bash unset, Windows paths and trailing slashes normalize,
  the spawned server receives the inline config alongside its password, and a
  user-supplied `OPENCODE_CONFIG_CONTENT` is preserved.
- No note format, setting key, review schedule or network default changed.
