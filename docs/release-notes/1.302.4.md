# 1.302.4 — An overnight run reports what it really did

## What the owner saw
A 100-PDF overnight import got through 47 files and closed with **0 files,
0 PDFs, 0 notes, 0 images**. The vault held one folder per attempted PDF, each
with an empty `images` subfolder and nothing else. The run was started with
**Start … files overnight** on the import window and had not paused or reloaded,
and it was running 1.302.3.

## What was wrong
- **No journal.** `PdfImportModal.showSetup()`'s overnight button only set
  `unattended = true` and called `startUnattended()`. The run journal
  (`mcq-tracker-overnight-runs`) is created by
  `plugin.startOvernightImport()`, which that path never called.
  `finishUnattended()` therefore summarized a `null` run through
  `runTotals(null)`, which returns zeros: the notice said 0 files and 0 notes,
  `writeOvernightLog()` was never reached with a run, pause/resume/undo had no
  entries, and `entryNeedsChecks` had nothing to check.
- **Leftover folders.** When a file failed before writing a note, the unattended
  error path recorded the result and moved on without removing what the attempt
  had already created (folder, `images` folder, extracted text, copied PDF), so
  a run whose files all failed left one empty folder per PDF.

## What changed
- `plugin.beginOvernightRun(files)` creates the journal for device files and
  vault paths, keeps the picked handles for resume, and stores it. The setup
  screen's overnight button calls it before `startUnattended()`.
- `plugin.overnightSummaryText(run, summary, modal)` reports notes written out
  of files queued, matched and flagged counts, and the first failure with the
  provider's own words. If a journal is genuinely missing it falls back to the
  modal's live results instead of printing zeros.
- `PdfImportModal.showError()` cleans up an unattended attempt that wrote no new
  note (`attemptWroteNotes()`), so its folder, images folder, text and copied
  source do not survive a failure. Cleanup lists the attempt's own files after
  the agent baseline, so a note the agent wrote is removed with it, while a
  folder holding a pre-existing note is never touched (plain `rmdir`, never
  recursive).

## Evidence
Headless Obsidian 1.15.1, the built bundle copied into a test vault, three PDFs
(`night-a.pdf`, `night-b.pdf`, `multi-1.pdf`) queued by clicking **Start 3 files
overnight** in the real import window, with OpenCode pointed at a dead port so
every file failed:

- journal: `night-mwhxk5jl-1-3`, status `finished`, three entries, all `error`
  with `OpenCode started, but its readiness check timed out…`;
- `Questions/night-a`, `Questions/night-b` and `Questions/multi-1` were all
  removed — no folder, no `images` folder, no copied PDF;
- `Overnight import log.md`: `Run night-mwhxk5jl-1-3 · status: finished` and
  `Files: 3 (0 done) · Notes: 0 · Matched: 0 · Flagged: 0 · Check errors: 0`;
- closing summary: `Overnight import finished: 0 notes from 0 of 3 files,
  0 matched, 0 flagged for review, 3 failed — OpenCode started, but its
  readiness check timed out. Press Test OpenCode again; …`.

Tests cover both halves: the setup-screen button creates a journal with a
`done` entry naming its notes and writes the log, and a zero-note attempt
removes its folder and `images` folder while a pre-existing note keeps its own.
