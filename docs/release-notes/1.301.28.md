# 1.301.28 — A frozen check recovers on every OpenCode setup

## What was wrong
1.301.27 recovered a frozen answer check by calling `ensureOpenCode()`. That is
right for the copy this plugin starts, but on a **manual** OpenCode setup
(`ai.managed` off, the user runs `opencode serve` themselves) it went on to
`manager.ensure()`, which found no managed binary and threw *"OpenCode isn't set
up yet…"*. Recovery then gave up and the note was kept unverified, with a
message about installing OpenCode the user does not need.

## What changed
- `recoverAiConnection()` restarts only the server the plugin started: managed
  setups still `manager.stop()` → `ensureOpenCode()`; a manual server is left
  alone (never killed, never re-downloaded, never replaced) and the retry is the
  recovery. Both still re-send the identical prompt with the same model.
- The notice for a manual server says *"OpenCode stopped answering, so this same
  answer is asked again..."*, so it no longer promises a restart it cannot have.

## Verification
- New test `answer verification: a server the user runs is asked again without
  being restarted` asserts two asks, `ensureOpenCode()` never called, `stop()`
  never called, and the note verified as a match.
- End-to-end run against a **real managed process** (a stand-in `opencode`
  executable spawned by the plugin's own manager, real HTTP, the shipped
  six-minute silence allowance):
  - first process accepted `POST /session/<id>/message` on port 36121 and never
    answered;
  - at 361 s the guard fired: *"OpenCode stopped answering, so it is being
    restarted, and then this same answer is asked again..."*;
  - the manager killed that process and `ensureOpenCode()` started a fresh one
    on port 38913;
  - the identical 197-character prompt was sent again (byte-identical);
  - result: `checked: 1, failed: 0`, `verification.status: "match"`.
- Suite: **2,804 pass, 0 fail**; `npm run check` clean; `main.js` 7,294,104
  bytes from 364 modules.
