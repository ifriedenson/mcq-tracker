# 1.302.5 — A spent free tier says so in seconds

## What the owner saw
A 100-PDF import failed file after file with:

> **Could not import** — OpenCode stopped answering while it was writing this
> file: nothing was written for 6 minutes. The plugin will restart OpenCode and
> start this file again once.

The files were full AP World chapters. The import was undone afterwards, which
removed 133 files and kept no notes (undo worked as designed).

## What was wrong
- **The provider's reason never reached the plugin.** OpenCode leaves an
  **empty, unfinished** assistant message behind a failed request and puts the
  reason only on its own event stream, as a `session.status` retry:

  ```json
  {"status":{"type":"retry","attempt":1,"message":"Free usage exceeded, subscribe to Go",
   "action":{"reason":"free_tier_limit","link":"https://opencode.ai/go"}}}
  ```

  and in its log as `stream error … Free usage limit reached`. The message the
  import polls has no `error`, no parts and no `time.completed`, which is the
  same shape as a model still reading a long prompt, so the import could only
  wait out its silence allowance, restart OpenCode, and hit the same wall for
  every file.
- **One silence allowance for every file.** `waitForAgent()` used a fixed
  six-minute `agentSilenceMs`, so even a genuinely slow read of a large chapter
  ended the same way.
- **A managed server was booted for a manual setup.** `ensureOpenCode()` called
  `manager.ensure()` unconditionally; with `ai.managed` off and a healthy server
  at the configured address, the manager still started the plugin's own OpenCode
  on a random port, and a cold start slower than 20 seconds failed the file with
  "OpenCode started, but its readiness check timed out".

## What changed
- `OpenCodeClient.watchEvents(onEvent, signal)` follows the server's `/event`
  stream (SSE over `fetch`, best effort). `PdfImportModal.watchAgentEvents(sid)`
  keeps the latest `session.status` and `session.error` for the file being
  written, `pollAgent()` returns `providerError` and `busy`, and
  `watchSession()` stops the file at once with the provider's own words.
- A `busy` status refreshes the quiet clock: the server saying it is working is
  not a stalled agent.
- `OpenCodeClient.send()`, the blocking call answer checks use, now watches
  the same stream while it polls: a `retry` status or a `session.error` ends
  the check at once with the provider's words and aborts the dead request, and
  a `busy` status refreshes its quiet-time clock. A live run showed ten checks
  waiting out their allowances after the free tier ran out.
- `isCapMessage()` treats `Free usage exceeded` like a spent request cap, so an
  overnight queue **parks with its files pending** instead of failing every
  remaining file. A transient 429 is still retried, never parked.
- `PdfImportModal.agentAllowanceMs()` adds about one second per thousand tokens
  of the file's own text to the six-minute base, capped at twenty minutes, so a
  slow read of a long chapter is not declared stalled while a frozen request
  still ends at the cap.
- `ensureOpenCode()` probes the configured address (4 seconds) when
  `ai.managed` is off and fails fast naming it, instead of starting the managed
  copy.

## Evidence
Headless Obsidian 1.15.1, the shipped bundle in a test vault, a five-PDF
overnight queue started from the import window against a manual OpenCode on
`127.0.0.1:8092`:

- The renderer's own `fetch` to that server is refused (`Failed to fetch`), so
  `watchEvents()` reads the stream with Node's `http`, the same way the
  OpenCode manager runs its child processes. With the Node reader the stream
  delivers `server.connected` and, while a file is being written,
  `session.status { type: "busy" }` — the import's status field showed `busy`
  throughout the run.
- The failing shape was captured from a live run: OpenCode logged
  `AI_APICallError: Free usage limit reached…`, the session's last assistant
  message had **no parts, no error and no completion time**, and the event
  stream carried
  `session.status → { type: "retry", message: "Free usage exceeded, subscribe to Go", action: { reason: "free_tier_limit" } }`.
  None of that reached the old plugin, which is why it waited six minutes and
  restarted into the same wall.
- The paused queue now says why in `Overnight import log.md`:
  `Paused: Free usage exceeded, subscribe to Go` — the provider's own
  sentence, taken from the event stream, on the line under the run header.
- On the fixed build, the same queue wrote notes for the first file
  (`Questions/multi-1`, 2 notes) with `manager.isRunning()` **false** the whole
  time — the manual server was used as it is — while the journal and
  `Overnight import log.md` recorded the run.
- With the manual server stopped, every file failed in seconds with
  "OpenCode at http://127.0.0.1:8092 isn't answering…" instead of a readiness
  timeout.

The retry path itself is pinned by a test that feeds a `retry` status through a
stand-in client's `watchEvents()` and asserts the file ends in well under a
second with the provider's sentence and the "waiting a few minutes" advice; a
second test pins `isCapMessage("Free usage exceeded, subscribe to Go")` while
`HTTP 429` stays retryable.
