# 1.285.0 — The knowledge record follows the note

This release extends the opt-in knowledge record from 1.283.0/1.284.0 so a
concept never orphans when its source note moves, is renamed, or is deleted and
recreated at a new path. There are no new dependencies, providers or external
services, and MCQ Tracker's own UI is unchanged except that a moved note keeps
its card instead of appearing as a new one.

## What changed

- **Stable note identity.** Every note entry now carries `noteId` (the hash of
  the path it was first indexed at), a bounded `pathAliases` list and a
  `contentHash`. Concept ids are derived from `noteId` rather than the current
  path, so they survive a move exactly as they already survived a heading
  rename.
- **Vault events drive the record.** `handleKnowledgeRecordRename`,
  `handleKnowledgeRecordDelete` and `handleKnowledgeRecordCreate` are registered
  in `startDeferredStartup` on the vault's `rename`, `delete`, `create` and
  `modify` events. A file or folder rename moves the existing entry and records
  the old path as an alias; a delete marks the entry `missingAt`; a create
  relinks by path alias or content hash.
- **Debounced incremental updates.** `scheduleKnowledgeRecordRefresh` coalesces
  changed notes (600 ms) and `flushKnowledgeRecordRefresh` applies them through
  `refreshKnowledgeRecordSource`, which rebuilds one entry and never rescans the
  vault. `scheduleKnowledgeRecordRebuild` / `flushKnowledgeRecordRebuild` cover a
  bulk restore; the full `rebuildKnowledgeRecord` remains the command path.
- **No duplicates, no double counting.** One record entry per source note is
  enforced on every path; a stale key is deleted before the new one is written.
  Evidence is always re-projected from the linked questions, so repeated
  rebuilds do not add attempts.

## Verified

`tests/knowledge-record-scenario.test.js` now drives the real plugin through:
build → attempt evidence → heading rename → note move (one question rewritten
to the new path, one still pointing at the old one) → note file rename →
delete → recreate at a new path → delete → restore at the same path, with a
full rebuild and a fresh plugin reload between steps. It asserts the note id,
every concept id, `firstSeen`, aliases, coverage/known/due, attempt counts, the
misconception open → fixed state, a single record entry per note, stable
idempotency after repeated rebuilds, the Insights card text (including
`source missing` only while missing) and the learner digest.

`node --test` → **2,379 tests pass, 0 fail**. `npm run check` is clean: no
dynamic code, the vendor guard passes, `main.js` is up to date and the plan
status is current. The generated capability inventory was regenerated.

## Limits

This is a harness verification, not a visual Obsidian pass. The scenario calls
the same vault handlers Obsidian calls (the fake app keeps one listener per
event, so it invokes the record's handler directly) and the same Insights and
digest code; it cannot reproduce Obsidian's own link rewriting, drag-and-drop
timing or a real sync restore. A human should still move a note in a real vault
and watch the card once.
