# MCQ Tracker 1.218.0

The PDF reader becomes a PDF editor. Reorder, rotate, duplicate, delete, merge
and extract pages, type text onto them, place images, stamp page numbers, crop
the margins, fill the PDF's form fields, and save a copy with your annotations
and form values burned in. The original file is never written.

This is the owner's reversal of the §11 **E4** gate ("keep annotation-only PDF
tools"), made on November 4, 2026 with permission to use MIT libraries. The
editor work was developed under the working number 1.217.0, which was never
published; it ships here as **1.218.0**, and the four fix patches
1.218.1–1.218.4 follow it.

## What changed

- **Undo and redo.** Every action that changes the document is one undoable
  step: rotating, moving, duplicating or deleting a page, adding a blank page or
  another PDF's pages, filling a form field, drawing the sidecar annotations into
  the pages, adding text, placing an image, stamping page numbers, and cropping.
  **Undo** and **Redo** sit above the page cards, disabled when there is nothing
  to do and named after the action they reverse ("Undo crop pages"); Ctrl/Cmd+Z
  and Shift+Ctrl/Cmd+Z (or Ctrl/Cmd+Y) do the same from the keyboard. A new edit
  discards whatever had been undone. Undo restores the whole document from bytes
  captured when that step was made, never by re-walking the window: undoing every
  step returns exactly the bytes that were read from the vault, and redoing
  returns the bytes each step saved. Nothing is written to the vault until
  **Save a copy**, which then clears the history so undo cannot contradict the
  file it wrote. The history is session-only and bounded — the opened file plus
  the last 20 steps, inside a 96 MB budget — so a long session cannot grow
  without limit.
- **Page operations.** Every page is a card with a preview and its own
  controls: rotate either way, move earlier or later, duplicate, delete, or tick
  it for extraction. **Add pages from a PDF…** appends every page of another PDF
  in the vault, **Add blank page** appends an empty page, and **Extract selected**
  writes the ticked pages into their own new PDF. A PDF always keeps at least
  one page, so the last delete is refused with a message.
- **Content editing.** An **Add content** section writes new material into the
  pages: typed text with a size, colour, font and one of nine anchor positions
  (top, middle or bottom, on the left, in the centre or on the right), a PNG or
  JPEG from the vault at a chosen width, `{n}` / `{total}` page numbers, and a
  crop box built from four margins. Each one targets a single page or every
  page. Text is wrapped to the page width, converted to characters a standard
  font can draw and clamped to 5,000 characters; a crop that would leave less
  than 36 by 36 points is refused; an image aimed at a rotated page is refused
  rather than placed at a guessed angle; and only PNG and JPEG are accepted, by
  their signature bytes. The page previews re-render from the edited document
  after each of these changes, so a crop or a stamp shows up at once.
- **Watermarks, document properties and splitting.** **Add watermark** writes one
  faint line of text across the page — size, opacity, colour, angle (0°, 30°, 45°,
  60° or 90°) and one page or all of them — shrunk automatically so it never runs
  off the page. A rotated page is refused rather than guessed at. The **Title**,
  **Author**, **Subject** and **Keywords** fields write the copy's document
  properties. **Split every N pages** writes `name (split 1).pdf`,
  `name (split 2).pdf` and so on beside the original, at most 100 files, with the
  last part holding the remainder. The watermark and the properties are ordinary
  undo steps; splitting is an export and leaves the edited document alone. These
  three came from the owner's PDFCraft reference and are built entirely on the
  vendored engine.
- **New form fields — authoring, not just filling.** The **New form field** section
  writes a field into the copy: a text field, a checkbox, a dropdown or a radio
  group, on any page, at a chosen position and size in PDF points, with its own
  default text, starting checked state, or comma-separated choices and initial
  choice. Names come from the label, keep letters, digits, dashes and underscores,
  and gain `_2`, `_3` … when that name already exists, so an existing field is
  never renamed or overwritten; a duplicate name asked for explicitly is refused
  instead. Saving builds each new field's appearance stream, so a normal viewer
  shows and can fill it; the form is never flattened and every existing value
  survives. A box outside its page, a box smaller than 8 by 8 points, an empty or
  repeated choice list, a choice that is not in the list and too many choices for
  the box are refused with a message rather than producing a broken field. Adding
  a field is one undo step named **add a form field**. This is the authoring half
  of the forms support the owner's PDFCraft reference has; like the rest of the
  editor it is built on the vendored engine.
- **Form filling.** Text fields, checkboxes, radio groups, dropdowns and option
  lists are edited in place. A value that is not one of the form's own choices,
  a field the PDF marks read-only, and a signature or button field are refused
  by name instead of being guessed at. **Flatten the form** bakes the appearance
  streams into the page content so the values can no longer be edited.
- **Annotations travel with the copy.** **Burn annotations into the copy** draws
  the sidecar's highlights, underlines, strike-throughs, boxes, ink strokes, text
  boxes and quoted selections into the page content, so the marks show in any
  PDF viewer. Positions are converted from the reader's normalized page
  coordinates into PDF points for `/Rotate` 0, 90, 180 and 270, and a page map
  keeps each annotation on its own page after pages are deleted or moved. An
  annotation whose page no longer exists is skipped and reported, never drawn
  somewhere else.
- **Nothing is overwritten.** Every save goes through `plugin.savePdfCopy`,
  which writes `name (edited).pdf`, then `name (edited 2).pdf`, beside the
  original and opens it. The source PDF, its content hash and its
  `.annotations.md` sidecar are untouched, so the existing annotation links keep
  pointing at the PDF they were drawn on. **Reset changes** reloads the original
  and discards everything.
- **Two ways in.** The command **PDF: open the editor (pages and forms)** (with
  a PDF open) and a new **Edit pages and forms** button in the reader, which
  saves unsaved marks first.

## Files

- `vendor/pdf-lib.js` — the unmodified `dist/pdf-lib.min.js` of pdf-lib 1.17.1.
- `src/pdf-editor.js` — the bounded, validated operations, including `addText`,
  `addPageNumbers`, `cropPages`, `addImage`, `addWatermark`,
  `setDocumentProperties`, `splitPdf` and `addFormField`. No Obsidian API, so the whole path runs
  under `node --test` with real PDFs.
- `src/pdf-editor-modal.js` — the window, its page cards, **Add content**
  section, watermark and document controls, **New form field** builder, split row,
  form rows, image picker, undo/redo row and footer.
- `src/pdf-editor-history.js` — the bounded byte-level history: state zero is the
  opened file, each step holds the serialized document next to the page map and
  annotation state, and a new edit drops the redo tail.
- `src/plugin.js` — `openPdfEditor`, `openActivePdfEditor`, `savePdfCopy` and the
  command; `src/pdf-ink-modal.js` — the reader's editor button.
- `styles.css` — `.qt-pdf-editor-*`.
- `NOTICES.md` and `docs/license-audit.md` — the pdf-lib entry, its MIT text, and
  the notices for the pako (MIT) and tslib (Apache-2.0) code inside that build.

## Boundaries

- **XFA forms** and **rewording the text already on a page** are not
  supported. Both are refused with a message; neither is approximated. New text
  is drawn on top of the page content; the existing run is never re-flowed or
  replaced. The editor works on the page tree, AcroForm fields, the page content
  it adds and the marks the plugin already stores. Placing an image needs a page
  that is not rotated, and text cannot be placed inside an existing column.
- Encrypted PDFs, files over 80 MB and documents over 2,000 pages are refused
  rather than half-loaded.
- A watermark needs an unrotated page, exactly like a placed image; a rotated
  page is refused instead of guessed at. Splitting and extracting write new files
  beside the original and never change the document being edited, so they are not
  undo steps.
- Document properties are written into the copy only; the source file's own
  metadata is untouched, like its pages and form values.
- A new field must fit on its page and be at least 8 by 8 points; a radio group
  needs 8 points of height per choice. Nothing is flattened, renamed or deleted:
  a label whose name already exists gets a numeric suffix, while an explicitly
  requested duplicate name is refused.
- The history is session-only: closing the window drops it, and saving clears it.
  Once more than 20 steps have been recorded the oldest intermediate steps are
  dropped (the opened file is always kept), so undo can jump back to the file as
  it was opened.
- While the window has focus its own shortcut owns Ctrl/Cmd+Z, including inside
  the **Add content** text box; a text field's native typing undo is not what
  that key does there. Edit the text itself in the field.
- No network request, server, provider, key or new package dependency was added.
  `package.json` still has no dependencies; the engine is vendored as a file, the
  same way ts-fsrs is.
- `main.js` grows by about 525 KB (the vendored engine) to 4.5 MB.

## Verification

**The engine.** `tests/pdf-editor.test.js` builds real PDFs with the vendored
engine and covers: opening and refusing empty or damaged files, rotation in every
direction, page move/duplicate/delete/blank insert, merging another PDF without
changing it, field discovery for all five supported kinds, filling and reloading
values, refusing a value that is not a choice, flattening a form, burning marks,
ink and text, the page map after a delete (including the orphan case), the
coordinate transform for all four rotations, extraction, and the never-overwrite
naming rule. Four more cover content editing: typed text on one page and on
every page with the empty and out-of-range refusals, a crop whose box and
untouched media box survive a save, page numbers with a format, a start offset
and a page subset, and a real PNG built in the test (zlib chunks with their own
CRC-32) placed on one page and all of them, plus the empty, non-image,
out-of-range and rotated-page refusals. Four more cover new form fields: each of the four types is added on a chosen page,
saved, reloaded and read back through pdf-lib's form API, checking its type, name,
page, widget rectangle and appearance stream, the checkbox's starting state, the
dropdown's choices and the radio group's one ring per option; a label colliding
with an existing field becomes `student_2` while the old field keeps its value,
and an explicit duplicate is refused; and eleven refusals (bad type, no name,
missing page, a box outside the page, a negative position, a 4-point box, empty and
repeated choice lists, a choice outside the list, too many rings for the box) are
rejected without adding anything. Three more cover the PDFCraft-style
additions: the properties round-trip through a save (trimmed, bounded, cleared
when absent, and refused with nothing to change); a watermark's text is found in
every page's decoded content stream together with its opacity graphics state, a
long one shrinks to fit, and empty, out-of-range and rotated-page requests are
refused; and splitting produces the right page counts, remainder part, page
indexes and refusals (zero pages, one-page document, more than 100 parts).

**The history.** `tests/pdf-editor-history.test.js` proves the stack on its own:
state zero is the opened bytes, undo walks back through every step and redo walks
forward to the bytes each step saved, a new edit after two undos drops the redo
tail, the step count and the byte budget both bound what is held without losing
the opened file, clearing after a save keeps one honest state, and junk input is
refused rather than thrown. Serialising edits turned out to be necessary: pdf-lib
serialises lazily, so two mutations in one tick produced identical bytes; every
mutation now runs through one queue that snapshots the document before the next
one starts.

**The window, as the plugin runs it.** `tests/pdf-editor-window.test.js` opens
the real `PdfEditorModal` on a real four-page PDF sitting in the mocked vault and
drives its own methods end to end:

- the window loads, reports `4 pages, 3 form fields`, draws four page cards and
  one row per form field, and leaves no unhandled rejection and no failure
  `Notice`;
- it rotates page 1, moves it to the third position, fills the text field and the
  dropdown through their rendered controls, toggles the annotation-burn and
  form-flatten checkboxes through their own change handlers, then saves;
- the bytes that reach `vault.createBinary` are read back with pdf-lib: four
  pages, the moved page's size in position three, `/Rotate 90` on it, and the
  saved field values. The source PDF's bytes are untouched;
- a second run writes `Papers/Exam (edited 2).pdf` instead of the first copy;
- the `pdf-edit` command opens the window on the active PDF and refuses a note
  or no file with **Open a PDF first**; the reader's **Edit pages and forms**
  saves unsaved marks first, then hands over its own path and closes;
- the engine is proved to arrive through `main.js` itself: the built bundle
  contains `__defs["vendor/pdf-lib"]`, and the editor exported by the bundle
  parses, edits and writes a PDF;
- typed text, a real PNG from the mocked vault, four crop margins and page
  numbers are driven through the rendered **Add content** controls, each
  reporting its own status line; the saved copy is read back with pdf-lib, and
  its crop boxes and untouched media boxes are the ones the window asked for
  while the source PDF stays byte-for-byte unchanged;
- a mixed stack — the annotation burn, a form field, a page rotation, page
  numbers, a crop and a placed image — is undone one step at a time through the
  rendered **Undo** button until the window's bytes equal the bytes read from the
  vault before any edit, then redone through **Redo** until they equal the edited
  bytes; the rotation, crop box and field value follow both directions, and
  neither direction writes to the vault;
- a new edit after two undos discards the redo tail, and undo then reaches the
  opened bytes instead of the dropped steps;
- a new text field and a new checkbox are driven through the **New form field**
  controls, the status line names each field and its page, each field is exactly
  one `add a form field` undo step, nothing is written before Save, undo restores
  the opened file byte for byte, and the saved copy reloads with both widgets on
  page 2, their appearance streams present and the earlier fields' values intact;
- the title field and a watermark are driven through the rendered controls, the
  window reports both, undo returns the opened bytes and redo brings the title
  back; splitting three pages per file writes `(split 1)` and `(split 2)` with
  three and one pages and leaves the edited document at four pages with no
  history entry;
- **Save a copy** writes the copy and clears the history to a single `Saved copy`
  state, so Undo is disabled again;
- an edit accepted in the same tick as a save is drained and snapshotted before the
  copy is written, so a fast click is never silently dropped;
- Ctrl/Cmd+Z, Shift+Ctrl/Cmd+Z and Ctrl/Cmd+Y run through the window's own
  keydown handler, and unmodified or Alt-modified keys change nothing;
- a truncated PDF is reported in the window instead of thrown.

Writing these found a real defect: `renderFields` used `return` instead of
`continue`, so only the first form field was ever drawn. It is fixed. The mocked
harness also gained the pieces this window needs and other tests can use: a
`Modal` with `app`, `open` and `close` (and a record of every modal opened), a
`FuzzySuggestModal` that can be opened, and `setAttribute`/`getAttribute` on the
fake DOM.

**The vendored engine.** `scripts/check-vendor.js` now runs inside
`npm run check`. It fails if `vendor/pdf-lib.js` is missing, if it is not exactly
525,099 bytes with SHA-256 `0f9a5cad…694f` (the published pdf-lib 1.17.1
`dist/pdf-lib.min.js`), if `src/pdf-editor.js` stops loading it as
`require("../vendor/pdf-lib.js")`, or if the build stops bundling it. The same
`verify()` is asserted by the window test, so the guarantee cannot rot silently.

**4,545,460 bytes of `main.js`, 1,683 tests pass / 0 fail**, `npm run check` is
clean across **272 source files**, and `git diff --check` is clean.

Known gate: no hand pass in a live Obsidian window, so these still need human
eyes on real hardware: whether the thumbnail previews look right, how a rotated
thumbnail reads, the page grid on a phone, form widgets as Obsidian and external
viewers paint them, and the visual result of burned annotations in an external
viewer. Behaviour is covered; appearance is not.
