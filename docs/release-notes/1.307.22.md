# 1.307.22 — The release checks itself

Released November 19, 2026. Obsidian 1.15.1.

## Why

Three separate holes let the release records drift apart, and none of them was
loud:

**A release could publish a bundle nobody verified.** `ci.yml` runs
`npm run check`, which includes the build check that proves the committed
`main.js` is a real build of `src/`. `release.yml` did not: it ran the tests and
the plan-status check and then published whatever `main.js` was committed. The
two workflows are independent jobs on the same push, with no `needs:` between
them, so a push with a stale bundle could turn CI red and still publish.

**A version could exist with no release.** 1.307.20 had a notes file, a
manifest that said `1.307.20` and its own built bundle on the PDF-import branch
(`350a117`), but the branch was merged as `1.307.21`. The release workflow reads
the version from `manifest.json` at the head of `main`, so 1.307.20 was never
tagged and never released, and nothing failed. The repository now has 382 tags
and 375 releases; 26 notes files have no tag.

**Tests could pass here and fail a time zone away.** The suite reads the clock,
and hardcoded dates had already cost two red days: 1.307.18 records two "every
Tuesday" tests that failed the day after they were written, and 1.307.21 had to
carry a `nextWeekdayKey` fix for the same cases.

## What changed

### A release verifies what it publishes

`release.yml` now runs `npm run check` on the exact commit it publishes, which
covers the build check, the duplicate and dynamic-code checks, the vendor pin,
the startup budget, the plan status and the new release-record check. It writes
`SHA256SUMS` for the three published assets, attests it with them, attaches it
to the release, and reads the release back afterwards instead of assuming the
create succeeded.

The silent `gh release create --target` fallback is gone. That path lets the
release API create the tag itself, which produces a **lightweight** tag: no
tagger, no date, no message, and nothing to sign. 114 of the 382 tags are like
that. A failed tag step now fails the release, with the log in the step summary,
rather than publishing a weaker ref.

The job's concurrency group is now per commit rather than per repository.
GitHub keeps one running and one pending job in a group, so a batch of quick
pushes used to cancel the middle release runs — the hole `repair-release.yml`
existed to patch.

### The release records are checked against each other

`scripts/check-release-notes.js`, run by `npm run check`, asserts that:

- `manifest.json` and `package.json` carry the same version;
- `versions.json` has that version, with the same `minAppVersion`;
- `docs/release-notes/<version>.md` exists (a release publishes that file);
- every notes version is either tagged, marked `Folded into: <version>` naming a
  tagged release, or one of the versions published before this check existed.

1.307.20's notes now say `Folded into: 1.307.21` in plain text. No release was
invented for it: its work shipped inside 1.307.21, and publishing a retroactive
1.307.20 would offer a downgrade to a build users were never served.

### The suite runs in three time zones

CI runs the suite in `UTC`, `Pacific/Kiritimati` (UTC+14) and `Etc/GMT+12`
(UTC−12), so a test that assumes the local date fails in the check instead of on
a release day. The far east leg is where the first run found its bugs, and the
far west leg is where a second pair surfaced; both directions are needed because
a hardcoded date can be wrong in either one.

### The repair workflow is manual and names what it repairs

`repair-release.yml` used to run on every push to `main` against four versions
hardcoded from 1.199 to 1.202, so at 1.307.x it re-checked ancient history and
could never repair the version that was actually missing. It is now a
`workflow_dispatch` taking the versions to publish; it finds each version's
release commit with `git log -S`, refuses a commit whose `manifest.json` says
something else, requires the notes file, creates an annotated tag and attaches
the checksums.

### Smaller hygiene

- **Pages** no longer redeploys the landing page for `docs/release-notes/**`;
  every release used to redeploy a site that had not changed.
- **`.gitattributes`** marks the generated `main.js` (7.3 MB) as binary and
  `linguist-generated`, so a release stops showing a multi-megabyte text diff
  and the build output stops counting as the repository's language.
- **Dependabot** watches the GitHub Actions versions weekly, in one grouped pull
  request. Actions are the only dependencies this repository has; the plugin is
  dependency-free by rule and `vendor/` is pinned by `check-vendor.js`.
- **`SECURITY.md`** gives malicious PDFs, paths outside the vault, leaked keys
  and model output that runs code a private reporting path through GitHub
  Security Advisories, with scope and a supported-version policy.
  `CONTRIBUTING.md` points at it.

## The three date bugs the new legs found

| Test | Assumption | Now |
| --- | --- | --- |
| `tests/spaced-everything.test.js` | the fixture was a UTC instant, but `{{date}}` renders the local date, so it read as the next day east of UTC | the fixture is built from local parts |
| `tests/memory-export.test.js` | `exportFileName` was given `Date.UTC(...)`, whose local date is the previous day west of UTC | local noon |
| `tests/task-recurrence.test.js` | the successor was compared with the UTC day, while the plugin advances from the local day | `T.util.localDate()`, the same basis the plugin uses |

`docs/capability-inventory.md` gains `tests/task-recurrence.test.js` in the
`util` row, because that test now cites the shared date helper.

## Evidence

- `npm test` in three time zones: **3,050 pass, 0 fail** in UTC, UTC+14 and
  UTC−12.
- `npm run check` clean, including the new release-record check and
  `main.js is up to date`.
- The new check refuses an untagged version: a probe
  `docs/release-notes/1.307.22.md` with no tag exits 1 with the version named,
  and passes again once the probe is removed.
- Every workflow `run:` block parses with `bash -n`, and all five configuration
  files parse as YAML.
- Before the change: 382 tags against 375 releases, 26 notes files without a
  tag, 114 lightweight tags, a 74.11 MiB pack built around a 7.3 MB committed
  bundle, and a repair list frozen at 1.199–1.202.

## Tests

No note format, setting key, review schedule or network default changed. The
plugin's own behaviour is untouched by this release: it is the pipeline, the
checks and the release records that changed.
