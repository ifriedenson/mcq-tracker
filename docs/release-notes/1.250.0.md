# 1.250.0 — Restyle a link's border and highlight

Released Nov 4, 2026.

## What changed

- **A link's visible styling is readable.** `readLinks` now reports `style` beside the page, target
  and area: `{ width, dash, highlight }` — the border width in points, the dash (`solid`, `dashed`,
  `dotted` or `custom` for a pattern this editor does not write) and the `/H` highlight mode
  (`none`, `invert`, `outline`, `push`).
- **And editable in place.** `updateLink` takes an optional `style` and writes it onto the same
  annotation: `/Border [0 0 width …]` and `/BS << /W width /S /S|/D /D [dash] >>` for the border, and
  `/H /N|/I|/O|/P` for the highlight. The page, `/Rect`, action or page jump and annotation identity
  are not touched, and the file still carries exactly one link.
- **Only what was chosen changes.** `style: { width: 4 }` keeps the dash and highlight the link
  already had, `style: { highlight: "outline" }` leaves its border alone, and a custom dash pattern
  is preserved when only the width is set.
- **The editor row.** **Add content → Links** gains **Width pt**, a **Border** dash select (keep,
  solid, dashed, dotted), a **Highlight** select (keep, none, invert, outline, push) and
  **Style link**, with a read-only hint that names the selected link's current style. It is one undo
  step, and only **Save a copy** writes.
- **Refusals, each with a message and no change:** a file with no links, a number outside 1 to the
  link count, an empty style (`{}`), a width that is missing, not a number, zero, negative or over
  24 points, a dash outside the offered set, a highlight outside the offered set, and a link whose
  `/BS` border style is neither solid nor dashed (`/B`, `/I`, `/U`) — which is preserved and refused
  rather than overwritten.

## Verification

- Three new engine tests and one new window test, written first and run against 1.249.0:
  `tests/pdf-editor.test.js` **69 pass / 4 fail** — `a fresh link has no visible border` reported
  `+ undefined` where `{ dash: 'solid', … }` was expected, and the link row read back without its
  new `style` key — and the window test **0 pass / 1 fail** with
  `error: 'the border width input is rendered'`. After the change: **73 pass / 0 fail** and
  **1 pass / 0 fail**.
- What they assert: `style: { width: 2, dash: "dashed", highlight: "invert" }` writes `/BS /W 2`,
  `/BS /S /D` with `/D [6 4]`, `/H /I` and `/Border [0 0 2 …]`, and the saved file reads back with
  the same page, area, address and a single annotation; width, dash and highlight can be changed one
  at a time without disturbing the others (and a solid border carries no `/D`); and every refusal
  leaves `/BS` absent, `/H` absent and the rectangle exactly as it was.
- The window test drives the real built `main.js`: it types **Width pt**, picks **Border: dashed** and
  **Highlight: invert** through the rendered inputs, presses **Style link**, checks the status, the
  single annotation, the unchanged box and target, one undo and one redo, a refused zero width, and
  the saved copy reopened with the style intact.
- Full suite **1905 pass**, `npm run check` clean across **297 source files**, `main.js` current
  across **298 modules** at **4,955,070 bytes**, and `git diff --check` clean.

## Limits

- **Border styles other than solid and dashed** (`/BS /S /B`, `/I`, `/U`) are preserved but refused
  for editing, and a `custom` dash pattern can be kept but not chosen.
- The rectangle is still given in percentages of the page box, and retargeting remains its own press
  (**Change link**) separate from **Move link**, **Move to page** and **Style link**.
